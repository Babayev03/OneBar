# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OneBar is a macOS menubar utility (SwiftPM executable, Swift 6 toolchain in Swift 5 language mode, macOS 26+). It bundles clipboard history with on-device OCR/QR, system stat rings, system-wide keyboard cleaning, prevent-sleep, and screen-region text/QR scanning. No third-party dependencies, no network calls — everything is AppKit/SwiftUI/Vision/IOKit/Carbon.

There is no test target and no linter config.

## Commands

```sh
swift build                 # debug build
swift build -c release      # release build
./build-app.sh              # release build → assemble dist/OneBar.app → ad-hoc sign → install to /Applications → relaunch
```

`build-app.sh` is the only way to actually *run* the app: the binary needs the `Bundle/Info.plist` (`LSUIElement`, bundle ID `com.onebar.app`) to behave as a menubar accessory.

The script signs ad-hoc but passes an explicit `-r='designated => identifier "..."'`. Without it codesign derives a designated requirement that pins the cdhash, which changes on every build — TCC then fails the app's Accessibility check while System Settings still shows the toggle on, so the permission-gated features die silently and `AXIsProcessTrustedWithOptions` won't even re-prompt (the stale row already exists, and the prompt only appears when there is none). Naming the bundle ID keeps the requirement identical across rebuilds, so the grant survives. The bundle ID is read out of `Info.plist` rather than repeated in the script; changing it still costs a one-time `tccutil reset Accessibility <id>` plus a re-grant, and moves the `UserDefaults` domain.

Regenerating the icon (rarely needed):

```sh
swift scripts/make-icon.swift
iconutil -c icns build/AppIcon.iconset -o Bundle/AppIcon.icns
```

## Architecture

`Sources/OneBar/` splits into `Services/` (behavior + state, all singletons), `Views/` (SwiftUI), and `Support/` (models, helpers).

**Everything is a `@MainActor` singleton.** Services are `static let shared` and most are `@Observable`, so views read them directly (`AppState.shared`, `SystemStatsService.shared`) rather than via `@EnvironmentObject`. The package builds with `-parse-as-library`.

**Two scenes, plus manually-managed windows.** `OneBarApp` declares a `MenuBarExtra` (`.window` style → `MenuView`) and a `Window(id: "preferences")` with `.defaultLaunchBehavior(.suppressed)`. Everything else — the clipboard panel, the keyboard-cleaning overlay, the HUD pill, the prevent-sleep status item — is an `NSPanel`/`NSWindow`/`NSStatusItem` created imperatively by its owning service. `AppDelegate` wires startup (start polling, start stats, register hotkey) and teardown.

**Settings live in `AppState`,** an `@Observable` singleton where every property has a `didSet` that writes to `UserDefaults` and defaults come from `defaults.register`. Adding a preference means: property + `didSet` + entry in the `register(defaults:)` dictionary + read in `init`. Changing a setting does not itself re-configure services — the Preferences panes call the side effect explicitly (e.g. `SystemStatsService.shared.restart()` after `statsInterval`, `startPolling()`/`stopPolling()` after the clipboard toggle). `keyboardCleaningActive`/`preventSleepActive`/`mouseMoveActive`/`autoClickActive`/`autoClickEditing`/`turboClickActive` are intentionally *not* persisted.

**Clipboard pipeline:** `ClipboardManager` polls `NSPasteboard.general.changeCount` every 0.5s, skips concealed/transient/auto-generated pasteboard markers and ignored source apps, dedupes identical text to the top, then enforces `maxImages` and `historyCap` (pinned items are exempt from both). Images are written as PNG files by `ClipboardStore` into `~/Library/Application Support/OneBar/images/`; `history.json` holds the metadata. OCR + QR run afterwards via `ImageAnalysisService` (Vision, off the main thread) and are patched back onto the item by id, so a `ClipboardItem` is mutable after insertion.

**Boot-scoped history:** `ClipboardStore` stamps `kern.boottime` (`BootTime.timestamp`) into `history.json`; on load, a boot-time mismatch beyond 5s drops all unpinned items and their image files. Pinned items always survive. This is the reason history "clears on restart".

**Clipboard panel keyboard model:** `ClipboardPanelController` owns a borderless non-activating `KeyablePanel` and installs three `NSEvent` monitors while visible — a local `keyDown` monitor (`handle(_:)` returns true to swallow the event), plus global and local mouse-down monitors for click-outside dismissal. `handle(_:)` branches on `isEditingSearch` (first responder is an `NSTextView`): bare-key bindings only apply when *not* typing. Esc unwinds one layer at a time: preview → action popup → search focus → hide. Selection/search/filter state lives in `ClipboardPanelModel`; `PanelAction.actions(for:)` derives the action list from the item's kind and whether OCR/QR/URL data is present.

**Shortcuts:** `ShortcutStore` maps `ShortcutAction` → `KeyBinding` (raw `keyCode` + modifier mask), persisted as JSON. Only `openPanel` is user-rebindable *and* global — every other binding is matched inside the panel's local monitor. Global hotkeys go through `HotkeyManager`, which uses Carbon `RegisterEventHotKey` (permission-free, unlike an `NSEvent` monitor, which would drag in Input Monitoring). It holds several at once, keyed by `GlobalHotkey` — whose raw values are Carbon hotkey ids, so never renumber a shipped case — and the C handler reads the fired id back out of the event with `GetEventParameter` because a C function pointer can't capture anything. Rebinding `openPanel` re-registers immediately.

**Permission-gated features:** keyboard cleaning (a `.cghidEventTap` `CGEvent.tapCreate` swallowing key events plus the `NX_SYSDEFINED` hardware-button subtypes — volume/brightness/media/eject/power — behind a `.screenSaver`-level overlay per screen; Touch ID is unaffected because fingerprint reads never produce a CGEvent) and pasting (`PasteService` synthesizes ⌘V via `CGEvent`) both require Accessibility and check `AXIsProcessTrusted()`; both degrade quietly rather than erroring. Scan Text/QR shells out to `/usr/sbin/screencapture -i -c` and needs Screen Recording — the `Process` must be retained in `ScreenCaptureService.runningProcess`, since a still-running deallocated `Process` crashes the app.

**Cursor movement is shared.** `Support/CursorMotion.swift` owns every synthetic pointer move: an eased 60fps path of `.mouseMoved` `CGEvent`s posted at `.cghidEventTap` (a single jump gets coalesced into no visible movement at all), with duration derived from distance ÷ speed so long and short moves look alike, and an optional `curve` that bows the path off the straight line via a quadratic bezier whose control point is randomised in size and side. Every step compares the cursor's actual position against the last one posted and returns `false` if they diverge — our own events land exactly where we put them, so any drift is a real hand on the mouse. Positions everywhere are read via `CGEvent(source: nil)?.location`, already in flipped top-left event space, which is why no multi-monitor coordinate conversion exists anywhere in the codebase except `NSScreen.eventSpaceOrigin` (used only to map nodes into a canvas window's view coordinates).

**Auto Mouse Move:** `MouseMoveService` sweeps the cursor out and back through `CursorMotion` (straight, `curve: 0`), which resets `HIDIdleTime` — the clock Teams/Slack read to decide you're away. In idle-aware mode the timer ticks faster than the configured interval and the nudge is gated on `CGEventSource.secondsSinceLastEventType(.hidSystemState, …)`, so real input postpones it rather than racing it. The return leg only runs if the outward one completed. `mouseMoveNatural` (on by default) curves the path, tilts the sweep off horizontal, varies its length, and jitters the timing — on a fixed schedule that means a one-shot timer re-armed with a fresh interval each tick, since there the interval is the only thing left to be regular; idle mode instead re-rolls its idle threshold per fire. Destinations go through `CursorMotion.clamp` first: a point past the screen edge is clamped by the WindowServer, and the cursor would then not be where we posted it, which `glide` would read as interference. Needs Accessibility, mirrors `SleepPreventionManager` for auto-off and the second status item.

**Auto Click:** three pieces. `ClickSequence` (in `Support/ClickNode.swift`) is the `@Observable` list of `ClickNode`s persisted to `UserDefaults` as JSON; positions are stored in event space so nothing is converted at run time. `ClickCanvasController` puts one transparent borderless `CanvasWindow` per display at `.statusBar` level hosting `ClickCanvasView` — click empty space to drop a point, drag to move, select for the inspector. `AutoClickService` walks the list: travel via `CursorMotion` with the configured curve, scatter the landing point by the jitter radius, act, then wait a delay randomised by the variance fraction. A node acts in one of four ways — click, type, slide or scroll. Typing overrides each event's unicode payload (`keyboardSetUnicodeString` on a `virtualKey: 0` event) instead of mapping keycodes, so it is layout-independent; newlines are sent as a real Return keypress because a literal `\n` in the payload is ignored by most text fields. A slide holds a button down along the path and posts its mouse-up on *every* exit path, since bailing out mid-drag would leave the system holding a button with nothing to release it. A scroll posts `scrollWheelEvent2` events with an explicit `event.location` — wheel events go to whatever is under the pointer, not to whatever has focus — and accumulates emitted distance across steps because integer wheel deltas would otherwise round small per-step amounts away to nothing. A double click is one event stream with `.mouseEventClickState` escalating — two plain clicks read as two singles — and the button is held ~20ms because a zero-length press is dropped by some controls. Three independent stops, because a running clicker owns your input: the Esc kill switch (a Carbon hotkey registered *only while running*, since a permanently held bare Esc would be swallowed system-wide), resistance stop (a `CursorMotion` glide returning `false`), and the auto-off timer. The canvas is flipped to `ignoresMouseEvents` during a run or it eats the very clicks being posted underneath it. `ClickLayoutStore` keeps named setups in `click-layouts.json` beside the clipboard history — on disk rather than in `UserDefaults`, since a layout is a file worth finding and backing up.

**Turbo click:** `TurboClickService` is deliberately *not* part of the sequence — it clicks wherever the pointer already is, reading `CursorMotion.location` every tick so it follows the cursor rather than latching a position. Starting it stops `AutoClickService`, since both drive the one pointer. Rate is capped at `TurboClickService.maxRate` (100/sec); Autoclick's author found macOS locks up past 900. It shares the Esc kill switch by registering the same `.autoClickStop` hotkey while it runs. Both it and the sequence post buttons through `Support/MouseEvents.swift`, so the events are identical — turbo skips the ~20ms hold because at high rates there is no room for one.

**Pick Color:** `ColorPickerService` shows `NSColorSampler`, AppKit's own loupe — sampling happens outside our process, so unlike Scan Text/QR it needs no Screen Recording grant. The sample is converted through `usingColorSpace(.sRGB)` before its components are read, since it arrives in the sampled display's own space and `redComponent` on a non-RGB colour traps. The formatted string (`ColorFormat` in `Support/Models.swift`) just goes on the pasteboard; `ClipboardManager`'s poll picks it up as an ordinary text item, so history and search come free. A `nil` callback is Esc and stays silent, like a cancelled `screencapture -i`.

**Display brightness:** `BrightnessService` picks one of four mechanisms per display, because no single one covers them all. The built-in panel and Apple's own externals (Studio Display speaks no DDC either) go through `DisplayServicesShim` — the private `DisplayServices` framework the brightness keys themselves use, `dlsym`'d and optional throughout, so a symbol Apple drops leaves one display uncontrollable rather than taking the app down. External monitors go over DDC/CI (`Support/DDC.swift`): I²C through the private `IOAVService` inside IOKit, wire format and IORegistry pairing derived from MonitorControl (MIT). Anything that won't talk DDC falls back to the gamma table, and AirPlay/Sidecar screens — which have no backlight and silently ignore gamma writes — are dimmed by `ShadeController`'s black window at `CGShieldingWindowLevel` (above the menubar, `ignoresMouseEvents`). Neither software path goes fully dark: a screen you can't see is a screen you can't undim. A display is "virtual" per CoreDisplay's own info dictionary, falling back to the *shape* of the vendor id — a real monitor's comes off its EDID chip and is 16 bits, while one invented in software gets ASCII ("aapl"/"airp"). DDC channel discovery walks the IORegistry pairing each `AppleCLCD2`/`IOMobileFramebufferShim` (which carries the EDID UUID, serial and registry path) with the `DCPAVServiceProxy` that follows it; matching *scores* candidates — registry path 10, vendor/product 2 each, serial 2 — and claims best-first, with discovery order breaking ties explicitly because `sort` isn't stable and two identical panels would otherwise swap displays between refreshes. Having a channel counts as DDC support; answering a read is a bonus, since plenty of monitors take writes while never replying. All of it runs on `DDCBackend`'s serial queue with a latest-wins coalescer — each I²C exchange sleeps for tens of milliseconds, so a slider drag would otherwise queue a backlog and the monitor would keep drifting after you let go. Tracking is a 0.15s poll rather than a notification, because reading DisplayServices is cheap and getting a private C callback signature wrong crashes the app; a 0.4s `lastLocalChange` window keeps our own writes from dragging the slider back, since the brightness keys *ramp* rather than jump. `forcedSoftware` (keyed on vendor-model-serial, which survives a replug) is the escape hatch for a monitor the probe guessed wrong about. Gamma outlives the process, so `restoreDimming()` runs on quit.

**Prevent Sleep:** `SleepPreventionManager` runs one session at a time, always with something that ends it — `SleepSession` is indefinite, `until(Date)` (the duration presets and "Until…" are the same thing, an end date computed when you pick it), `whileAppRuns`, or `whileFileGrows`. It holds two `IOPMAssertion`s: preventing system sleep says nothing about the display, so without the second the screen still goes dark while the Mac stays up — together they are `caffeinate -di`, system-only is `caffeinate -i`. Closing the lid is a *separate* path that ignores assertions entirely, so `Support/Clamshell.swift` drives it directly through `kPMSetClamshellSleepState` (command 12 on `IOPMrootDomain`'s user client — it reaches C but not Swift, hence the literal). No entitlement, no helper, no password; Amphetamine, sandboxed and App Store signed, does the same. Restoring always writes even with no connection of our own open, because a force quit leaves the switch set with nobody to clear it — which is why `AppDelegate` clears it blind at launch. Do **not** branch on `AppleClamshellCausesSleep`: on Apple silicon it reads `No` at rest while lid close still demonstrably sleeps the Mac. One 1s ticker drives everything (countdown, the file every 5 ticks, the battery every 30) rather than a timer per concern. The download watch is Amphetamine's model — end once the file stops growing — with two wrinkles: finishing *renames* rather than deletes (`Foo.dmg.download` → `Foo.dmg`) so the watch follows the rename in either direction, and a Safari `.download` package is a *folder* whose own size never moves however much arrives inside it, so a directory is measured by its contents. The enclosing folder is read once at pick time, while the user is still at the keyboard: asked an hour later the TCC prompt just sits there unanswered and the session never learns the download finished. Starting a session replaces the current one rather than stacking (two sets of assertions would need two stops), and `tearDown()` is the single release point so no exit path can leave an assertion or the lid switch behind.

**Sound:** `SoundService` drives system volume, mute and output-device switching straight off the CoreAudio HAL, with `Support/CoreAudioProperty.swift` as the leaf helper (address/exists/isSettable/value/setValue/objectIDs/string/channelCount, plus `CoreAudioListener`). Reads are cheap and writes are not, and that asymmetry shapes the whole file. A full read sweep of every device on both scopes is ~1.6ms, so reads stay synchronous on the main actor with no `lastKnown` cache — but a *single* `AudioObjectSetPropertyData` volume write measured 5ms to the built-in speakers, 11ms to AirPods and 17ms to a virtual driver, against a 16ms frame. (An earlier version of this note claimed writes returned "in tens of microseconds" and used that to justify writing inline; that was never measured, and a slider drag stalled the UI outright until it was.) Writes therefore go through a latest-wins coalescer onto `writeQueue` — `BrightnessService`'s machinery with the timing turned around: there the problem is that an I2C exchange *sleeps* for tens of milliseconds, here it is only that the main thread must not be the one waiting. `pending` holds at most the newest value per *(device, scope)*, so releasing a slider leaves no backlog draining into the device, and a group's fan-out (one write per member) costs the UI nothing. Still no lock and no ramp to wait out. `writeVolume`/`writeMute`/`write`/`scalar` are `nonisolated static` for exactly this reason and take a `memberControls` snapshot rather than reaching for main-actor state. "Has a volume control" is a property of a *(selector, scope, element)* triple, not of a device, so each one is probed down a ladder needing both `exists` and `isSettable`: `kAudioHardwareServiceDeviceProperty_VirtualMainVolume` (`'vmvc'` — the *functions* are deprecated, the selector is not, and it is what Control Center drives) → main-element `VolumeScalar` → per-channel scalars on the device's own `PreferredChannelsForStereo` pair (read = loudest channel, write = scaled by each channel's ratio to the peak, so a channel pulled down stays proportionally down) → `.none`, a disabled slider and a note. A device with no real mute control gets no mute button rather than a faked set-to-0-and-restore, which would be a second, disagreeing mute state that the volume keys and Control Center know nothing about. Enumeration needs output channels **and** `DeviceCanBeDefaultDevice` — the Teams loopback driver has two output channels and cannot be made default, and System Settings hides it for the same reason. Switching sets `DefaultOutputDevice` *and* `DefaultSystemOutputDevice` (app audio and alert sounds are separate properties), the second guarded on `DeviceCanBeDefaultSystemDevice`. Live tracking is `AudioObjectAddPropertyListenerBlock` on a dedicated serial queue — never `nil` (the HAL's own thread) and not `.main` — with the handler stored under a `@convention(block)` type, since Swift imports the listener typealias as an ordinary closure and bridges a *fresh* block per call site, so add-then-remove with "the same closure" would remove nothing and `AudioObjectRemovePropertyListenerBlock` returns `noErr` either way. Echo suppression is *not* brightness's blanket window: DDC ramps and CoreAudio doesn't, and a held volume key steps every ~100ms, so an echo is only ignored while it is near what we just wrote — one that lands far away is a device that took the write and ignored it, and the slider should snap back and show that. `lastWrite` is stamped again when the write actually lands, not only when it was asked for: with writes queued, the echo's clock starts at the far end. Note the volume keys go dead while Keyboard Cleaning is on, since its tap swallows the `NX_SYSDEFINED` subtypes by design; that is expected, and they must not be re-implemented off that tap. The input half is the same ladder at `kAudioObjectPropertyScopeInput` (where the `.none` rung is real — the Continuity iPhone microphone has no volume control at any element), except that there is only `DefaultInputDevice`; the HAL has no system input. The level meter is the expensive part: there is no level property anywhere in CoreAudio (`VolumeDecibels` is the knob's position, not the signal), so `Support/InputMeter.swift` opens the device with an `AudioDeviceCreateIOProcIDWithBlock` IOProc — not `AVAudioEngine`, whose input node follows the system default and so can't meter a non-default device — and that lights the orange microphone dot for as long as it runs. Hence `soundInputMeterEnabled` defaults to off, and even when on the meter starts from `SoundScreen.onAppear` rather than the menu's, which is the real reason `startTracking()`/`stopTracking()` exist. `NSMicrophoneUsageDescription` is mandatory in `Bundle/Info.plist`: without it the process is *killed* on first microphone access, not merely denied.

**Output groups:** playing to several devices at once — Audio MIDI Setup's "Multi-Output Device" under a name people recognise. `Support/AudioGroup.swift` holds the `OutputGroup` definition, `OutputGroupStore` (JSON beside the clipboard history and click layouts) and `AggregateDevice`, which builds one via `AudioHardwareCreateAggregateDevice`. `kAudioAggregateDeviceIsStackedKey` must be **1**, and this is one to trust the measurement over the header on: the header says a value of 0 means "the output streams are all fed the same data", but `stacked = 0` actually yields 4 channels in *two* streams (starting at 1 and 3), so ordinary stereo playback writes channels 1-2 and reaches the first member only — which is exactly what a broken group sounds like. `stacked = 1` yields 2 channels in *one* stream, which is what feeds every member alike. `AggregateDevice.isMirrored` re-checks the stored composition on every reconcile so a group built the wrong way round is rebuilt rather than left silently half-working. F11/F12 would otherwise **do nothing while a group is selected** — they ask the current output device to change its own volume, and a group genuinely has none, which is the standing complaint about macOS multi-output devices. `VolumeKeyMonitor` fixes that by tapping `NX_SYSDEFINED` subtype 8 and handing sound-up/down/mute to the same fan-out the slider uses. The tap exists **only while a group is the default output**, started and stopped from `refresh()`: every other device answers the keys itself, and taking them over then would be replacing working behaviour with an imitation of it. It needs Accessibility but never prompts for it — arriving at a permission dialog because you picked an audio device would be baffling, so without the grant the keys stay as dead as they were and the slider still works. It also stands down while `keyboardCleaningActive`, since that tap swallows the same events on purpose so wiping the keyboard can't change the volume. Members are stored as **UIDs**, never `AudioObjectID`s, and the first is the clock master: two devices have two crystals ticking at slightly different rates, so every other member gets `kAudioSubDeviceDriftCompensationKey`. Three things are measured, not assumed. An aggregate **inherits `canBeDefaultDevice` from its members**, so one member that can't be a default device yields a group that is silently absent from every device list with no error to explain it — which is why candidates come from `SoundService.groupCandidates`, i.e. the already-filtered `outputs`. The group has **no volume and no mute at any element** (this is the standing complaint that the volume keys stop working under a multi-output device), so `VolumeControl.group`/`MuteControl.group` fan the slider out to the members through each member's own rung of the ladder, using `memberControls` cached at refresh rather than re-probing on every tick of a drag. And `kAudioAggregateDeviceIsPrivateKey` must be **false**: private keeps the device out of other processes *and* out of being selectable, which is the entire point. The store is the source of truth — `reconcileGroups()` rebuilds any definition the HAL has lost and destroys any aggregate of ours that no definition claims (a stray left by a crash), guarded by a `reconciling` flag because creating or destroying a device fires the device-list listener straight back into `refresh()`.

**Per-app volume:** `AppAudioService` gives each app its own level without an audio driver, over macOS 14.2+ process taps (`Support/AudioProcess.swift`, `Support/AppMixer.swift`). Background Music and SoundSource both install a virtual sound card and *become* the default output device; OneBar is ad-hoc signed with no installer, so it taps instead. `NSAudioCaptureUsageDescription` is mandatory and the grant is TCC's "System Audio Recording". Five things here were each established the hard way, and every one of them fails *silently* — the slider simply does nothing:

- **`CATapMuted` alone does not mute.** The header says "no audio is sent from the process to the audio hardware", but a tap nobody reads appears not to run at all. Mute is therefore a gain of zero through the same mixer as every other level — one path, not two, and the working one.
- **The tapped process is not the app.** A browser plays through a helper (`com.apple.WebKit.GPU`), whose parent is launchd, so neither bundle id nor parent pid leads back to Safari. `responsibility_get_pid_responsible_for_pid` (dlsym'd, optional) is how the system itself attributes a helper to its app, and it is what makes "Safari" work. A process with no Dock app behind it is a daemon, not an app — `com.apple.CoreSpeech` holds an audio stream open permanently and must not be offered a slider.
- **One mixer per app, never one shared.** Taps arrive as input streams in an order nothing guarantees matches the order they were listed, so a shared mixer applied Safari's level to Music's audio. A single tap per aggregate makes the mapping trivially right, and keeps adding one app from interrupting another's playback.
- **Never rebuild the mixer unconditionally.** Creating a tap changes the process list and creating an aggregate changes the device list; both fire listeners that land back in `refresh()`, so an unguarded rebuild tears the device down and recreates it forever and never renders a single buffer. Rebuild only when the tap set or output device actually changes.
- **The device-bound tap variant (`processes:deviceUID:stream:`) renders nothing** when its aggregate also holds that same device. It reads like the right API — "streams destined for the selected device" — and it is a dead end; use the plain stereo mixdown.

A managed app keeps its tap **even at 100%**: dropping the route at 100% and rebuilding it at 99% is an audible click on every crossing, because the app's own output is cut and ours takes over. Holding it open costs one handover when the app is added and none afterwards, so an app on the list is always in OneBar's path and an app off the list is never touched. The render block is real-time — no locks, no allocation, no logging — which is why the gain lives in plain C memory and slides to its target over ~5ms rather than stepping. `AppMixer.renderCount` exists because "started" only means the call returned; a loop stuck at zero renders is the signature failure, and a commented-out row in `SoundScreen` prints it.

**Menubar label:** `MenuBarExtra` mangles stacked/inline views in its label, so the live CPU/MEM readout is pre-rendered to a single template `NSImage` via `ImageRenderer` in `MenuBarLabel.statsImage`.

## Conventions

- Use `.liquidGlass(in:)` (`Support/LiquidGlass.swift`) for glass surfaces rather than calling `glassEffect`/`.ultraThinMaterial` directly — it holds the macOS 26 availability fallback in one place.
- Transient user feedback goes through `HUD.show(_:symbol:)`, not alerts.
- Timers are created with `Timer(...)` + `RunLoop.main.add(timer, forMode: .common)` so they keep firing during menu tracking; callbacks hop back with `Task { @MainActor in ... }`.
- Comments in this codebase explain *why* a non-obvious workaround exists (AppKit quirks, permission behavior). Match that — don't add narration of what the code plainly does.
