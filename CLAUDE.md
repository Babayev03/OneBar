# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OneBar is a macOS menubar utility (SwiftPM executable, Swift 6 toolchain in Swift 5 language mode, macOS 26+). It bundles clipboard history with on-device OCR/QR, system stat rings, system-wide keyboard cleaning, prevent-sleep, and screen-region text/QR scanning. No third-party dependencies, no network calls — everything is AppKit/SwiftUI/Vision/IOKit/Carbon.

There is no linter config. There is a test target (`Tests/OneBarTests/`, `swift test`, 97 tests in
11 suites) covering the shelf's pure logic — file ownership, transfers, window geometry, action
availability, transforms, command search, instant-action layout and placement, custom-script
running, folder-watch rules, and `onebar://` parsing. It is not a general test suite: everything
else in the app is AppKit-bound and is verified by hand.

## Commands

```sh
swift build                 # debug build
swift build -c release      # release build
./build-app.sh              # release build → assemble dist/OneBar.app → ad-hoc sign → install to /Applications (or ~/Applications) → relaunch
```

`build-app.sh` is the only way to actually *run* the app: the binary needs the `Bundle/Info.plist` (`LSUIElement`, bundle ID `com.onebar.app`) to behave as a menubar accessory.

The script signs ad-hoc but passes an explicit `-r='designated => identifier "..."'`. Without it codesign derives a designated requirement that pins the cdhash, which changes on every build — TCC then fails the app's Accessibility check while System Settings still shows the toggle on, so the permission-gated features die silently and `AXIsProcessTrustedWithOptions` won't even re-prompt (the stale row already exists, and the prompt only appears when there is none). Naming the bundle ID keeps the requirement identical across rebuilds, so the grant survives. The bundle ID is read out of `Info.plist` rather than repeated in the script; changing it still costs a one-time `tccutil reset Accessibility <id>` plus a re-grant, and moves the `UserDefaults` domain.

Regenerating the icon (rarely needed):

```sh
swift scripts/make-icon.swift
iconutil -c icns build/AppIcon.iconset -o Bundle/AppIcon.icns
```

## Architecture

`Sources/OneBar/` splits into `Services/` (behavior + state, all singletons), `Views/` (SwiftUI), and `Support/` (models, helpers).

**Everything is a `@MainActor` singleton.** Services are `static let shared` and most are `@Observable`, so views read them directly (`AppState.shared`, `SystemStatsService.shared`) rather than via `@EnvironmentObject`. The package builds with `-parse-as-library`.

**Two scenes, plus manually-managed windows.** `OneBarApp` declares a `MenuBarExtra` (`.window` style → `MenuView`) and a `Window(id: "preferences")` with `.defaultLaunchBehavior(.suppressed)`. Everything else — the clipboard panel, every shelf, the notch drop target, the keyboard-cleaning overlay, the HUD pill, the prevent-sleep status item — is an `NSPanel`/`NSWindow`/`NSStatusItem` created imperatively by its owning service. `AppDelegate` wires startup (clipboard polling, stats, Brightness/Sound/AppAudio, `ShelfManager.start()` and with it the drag observer, the global hotkeys, and clearing a clamshell override left by a previous run) and teardown.

**Settings live in `AppState`,** an `@Observable` singleton where every property has a `didSet` that writes to `UserDefaults` and defaults come from `defaults.register`. Adding a preference means: property + `didSet` + entry in the `register(defaults:)` dictionary + read in `init`. Changing a setting does not itself re-configure services — the Preferences panes call the side effect explicitly (e.g. `SystemStatsService.shared.restart()` after `statsInterval`, `startPolling()`/`stopPolling()` after the clipboard toggle). `keyboardCleaningActive`/`preventSleepActive`/`mouseMoveActive`/`autoClickActive`/`autoClickEditing`/`turboClickActive` are intentionally *not* persisted.

**Clipboard pipeline:** `ClipboardManager` polls `NSPasteboard.general.changeCount` every 0.5s, skips concealed/transient/auto-generated pasteboard markers and ignored source apps, dedupes identical text to the top, then enforces `maxImages` and `historyCap` (pinned items are exempt from both). Images are written as PNG files by `ClipboardStore` into `~/Library/Application Support/OneBar/images/`; `history.json` holds the metadata. OCR + QR run afterwards via `ImageAnalysisService` (Vision, off the main thread) and are patched back onto the item by id, so a `ClipboardItem` is mutable after insertion.

**Boot-scoped history:** `ClipboardStore` stamps `kern.boottime` (`BootTime.timestamp`) into `history.json`; on load, a boot-time mismatch beyond 5s drops all unpinned items and their image files. Pinned items always survive. This is the reason history "clears on restart".

**Clipboard panel keyboard model:** `ClipboardPanelController` owns a borderless non-activating `KeyablePanel` and installs three `NSEvent` monitors while visible — a local `keyDown` monitor (`handle(_:)` returns true to swallow the event), plus global and local mouse-down monitors for click-outside dismissal. `handle(_:)` branches on `isEditingSearch` (first responder is an `NSTextView`): bare-key bindings only apply when *not* typing. Esc unwinds one layer at a time: preview → action popup → search focus → hide. Selection/search/filter state lives in `ClipboardPanelModel`; `PanelAction.actions(for:)` derives the action list from the item's kind and whether OCR/QR/URL data is present.

**Shelf:** a drag-and-drop stash, on Dropover's model — shake the cursor mid-drag or drop on the notch, a panel appears, you drop things into it, navigate anywhere, then drag them back out together. A shelf **references**; it does not copy. A dropped file stores its path *and* a bookmark, and `ShelfItem.resolveURL()` tries the path first — the cheap check, and right until the file moves — then falls back to the bookmark, which survives a rename. Text and image *data* has no file anywhere, so `ShelfStore` writes one into `~/Library/Application Support/OneBar/shelf-items/` and flags the item `isMaterialised`; that flag is the entire ownership model, and it is what makes dragging dropped text into Finder produce a real `.txt`. Every materialisation gets **its own UUID directory**, including each file delivered by one multi-file promise (`adoptPromisedFile`), because two items sharing a directory means removing one deletes the other's file. `discard` never trusts the persisted flag alone — it deletes only inside `shelf-items`, so a corrupt flag can never take a user's file with it — and `sweep(keeping:)` runs at launch to clear materialisations belonging to no surviving shelf. Pinned shelves are restored from `shelves.json` at launch; closing an unpinned one leaves a snapshot on a short recents list, which is the undo for closing a shelf you still needed.

**Shelf drag out** is where the semantics live. `ShelfDragSourceView` is AppKit rather than SwiftUI's `.draggable` because SwiftUI hands over an `NSItemProvider` and never says whether the destination moved or copied — and that answer is what decides whether the item stays on the shelf. `draggingSession(_:sourceOperationMaskFor:)` returns `[.copy, .move]` for `.outsideApplication`, which buys native behaviour for nothing: same volume moves, different volume copies, ⌥ forces copy. Narrowing that return to `.copy` is the whole implementation of the "always copy" preference. Drops *in* go through `ShelfDropView`, which registers for the dragged types plus `NSFilePromiseReceiver` — Photos, Mail and some browsers hand over a promise rather than a URL, and without the receiver those drops silently produce nothing at all.

**Shelf activation:** `ShelfDragObserver` is the one observer of real drags, and it feeds shake recognition and the notch target *independently*, so the notch keeps working when shake is off or the front app is on the shake ignore list. Mouse monitors need no permission — only keyboard ones would, which is why `HotkeyManager` goes through Carbon — but a mouse drag is not necessarily a *file* drag, so everything is gated on `NSPasteboard(name: .drag).changeCount` leaving its baseline. Window drags, video scrubbing and rubber-band selection never touch it. A 60fps poll runs beside the monitors because Finder can hand control to its own `NSDraggingSession` before a global monitor sees a single dragged event, while always updating the drag pasteboard. `ShakeDetector` owns no monitors at all: it counts axis-direction reversals in a 0.6s ring buffer, where a leg counts only once it exceeds the sensitivity's minimum length — that length is what separates a shake from hand tremor — with a 1.2s cooldown so one shake makes one shelf.

**Drop to notch:** `NotchDropController` puts a drag-only window over the camera housing of a display whose `safeAreaInsets.top > 0` *and* whose `auxiliaryTopLeftArea`/`auxiliaryTopRightArea` leave a gap between them. The target reaches `notchTargetDepth` below the housing, since a destination confined to the obscured strip is unhittable. Ending a drag is deferred while the pointer is still over the target: Finder momentarily reports `pressedMouseButtons` as zero while its dragging session is still live, so the destination callbacks — not the mouse state — are the authority on whether the drag has really left. The rim and bloom constants in `ShelfWindowGeometry` were fitted against Dropover screenshots rather than guessed, and the measurements are recorded beside them.

**Shelf windows:** one `ShelfPanel` per shelf, borderless + `.nonactivatingPanel`, brought up with `orderFrontRegardless()` rather than made key — a shelf appears in the middle of a drag out of another app, and taking focus there would end it. *When* it takes focus is `ShelfFocusIntent`, one value per creation path, because they genuinely differ: a shelf restored at launch takes none (activating at login would be rude), one the user asked for takes it at once, and one summoned mid-drag waits for its first drop — which is what makes the shelf keys work without clicking it first. Taking focus means `makeKeyAndOrderFront` **and** `NSApp.activate`: with another app frontmost, a key panel still does not receive keys. Two departures from `ClipboardPanelController` follow from that: there is deliberately **no** click-outside dismissal monitor, which would destroy the shelf the instant you began the next drag toward it, and focus is taken only where typing demands it (Customize, inline rename). `ShelfWindowGeometry` keeps every frame calculation as pure functions, so docking, retracting, clamping and snapping are unit-tested without a window on screen. A docked shelf collapses to a tab that peeks on hover; several docked on one edge stack by `collapseStackOffset`.

**Shelf actions:** `ShelfAction` is the menu, and `isAvailable(for:)` is a pure function of the acted-on items, so the whole list is tested without a window. Two rules are load-bearing. A right-click outside the current selection takes over the selection first, as Finder does — otherwise the menu would silently apply to whatever was selected somewhere else. A right-click also *commits a peek*, exactly as a left click does: without that the menu opens, the hover watch sees the pointer move onto the menu — which is outside the shelf — and slides a retracted shelf back under it. And **Move to Trash is offered only for the user's own files**: a materialised item lives in Application Support, and trashing that would hand someone OneBar's own scratch file, which Remove From Shelf already deletes. The menu raised on an item is built in AppKit (`ShelfActionMenu`) because it needs `NSSharingServicePicker`'s `standardShareMenuItem` — the system's own share menu, carrying AirDrop, Mail and the user's "More…" configuration — and an Open With list built from the apps that can open *every* selected file rather than just the first. The overflow section and the empty-space menu show neither and stay in SwiftUI. `NSMenuItem.target` is weak, so the view raising a menu owns a `ShelfMenuResponder` for as long as the menu lives.

**A shelf limit** (`shelfMaxCount`, five by default) caps how many are open at once, because each one is a live window that redraws with everything else and a docked one keeps a pointer watch running — a lot of them is felt as frame rate, not just counted. Going over it is **refused**, not made room for: a shelf holds what the user put on it, and quietly retiring the oldest to satisfy a shake would take a decision that is theirs. Pinned shelves beyond the limit stay pinned at launch rather than being dropped (`ShelfArchiveLogic.split`), so they are still listed as closed and can be brought back by hand.

**Shelf auto-retract** sends a shelf to `shelfAutoRetractEdge` rather than the nearest edge — a shake happens wherever the pointer is, so "nearest" scatters shelves across both edges — and gives a shake-made shelf the placement every other shelf already gets before it collapses. That placement (`defaultPlacement`) is the location preference nudged clear of the shelves already on screen, and it is the reason a column of shelves made by dropping on the notch comes out tidy: those go through it at creation, while a shake lands under the pointer and skipped it, then kept that height all the way to the edge. Both routes now end in the same column. The row is applied through `collapseRow`, carried into the collapse *animation* rather than written to the panel beforehand, since setting it first made the shelf visibly jump before it slid to the edge. `collapseRow` is also what clustering reads, **never the window's live frame**: animating the vertical position as well as the horizontal one means a restack landing mid-slide would otherwise read a Y the shelf is only travelling across, put it in a row it is not in, and commit the depth that came out of that — leaving a shelf inset with nothing in front of it long after the animation ended. `scheduleRestackSettle` runs the pass again once the animations have landed, as a second line of defence.

**`action-output` is never tidied automatically.** An output is a file the user asked for, so nothing deletes it behind their back; Preferences shows what the folder holds and offers to reveal or clear it. Clearing leaves any shelf item still pointing at one showing as missing, which the pane says.

**Shelf transforms:** Compress, Convert/Resize Image and Merge to PDF are the actions that *write*, and they all write into `~/Library/Application Support/OneBar/action-output/` — never beside the input, so a conversion cannot damage the original. Outputs are added to the shelf as ordinary **non-materialised** items: an action's output is the user's file, so taking it off the shelf leaves it on disk and Move to Trash is offered for it, which is the opposite of what a dropped-text materialisation gets. One transform per shelf at a time (`beginActivity`), since two runs would race for the same output name. `ShelfProgressPanel` is a window of its own rather than a line in the shelf — separate from `ShelfDialog` on purpose, since that one is exclusive and opening ⌘K mid-run would tear the progress down. Its bar is determinate only where a fraction is honestly known (n of m files); `ditto` reports nothing about how far into an archive it is, and inferring one from the output size would be a bar that lies for anything compressible, so compress gets an indeterminate one. Stop has to reach the *tool*, not just the Swift task: a cancelled task does nothing to a `ditto` already several seconds into a large archive, so `runTool` terminates the process — guarded, because `terminate()` raises on one that never launched, and cancellation can arrive first. The work is awaited directly rather than through `Task.detached`, which is deliberately independent of its parent and so would have let Stop clear the footer while the run carried on. Four things here are less obvious than they look:

- **`ditto` archives one source**, so several items are staged under a folder first. On APFS a same-volume `copyItem` is a clone, so that costs neither time nor space in the ordinary case. Two items on one shelf can share a file name and come from different folders, and staging both under that name silently loses one — the second is numbered the way Finder numbers it, and the staging copy is *not* swallowed with `try?`, because a half-built archive is worse than an error.
- **Image conversion goes through `CGImageSourceCreateThumbnailAtIndex`**, not a full decode and redraw. It is the efficient path, and `kCGImageSourceCreateThumbnailWithTransform` bakes in EXIF orientation — without it a photo shot sideways comes out sideways in a format with nowhere to record the rotation.
- **`ImageActionRequest.format` is optional, and `nil` means "keep whatever each file already is."** One request covers several files of different formats, and only `nil` can say that — which is what makes resizing a PNG produce a PNG. The resize presets leave it unset; the convert presets set it.
- **Resizing never upscales.** Asking 2048px of a 900px photo returns 900, so a preset larger than the original is a no-op rather than a blurry blow-up, and the pixel size only enters the output's name when the image actually shrank.
- **WebP is not an Image I/O destination on any current macOS.** The system reads it and cannot write it — the writable list is JPEG, PNG, HEIC, TIFF, AVIF and friends, measured rather than assumed. `WebPEncoder` shells out to `cwebp` where it is installed and `ImageFormat.available` drops the format where it is not, because an option that always errors is worse than no option. The pixels handed to `cwebp` go through a lossless PNG intermediate, so the resize and orientation fix survive. AVIF needs none of this and is native.
- **Remove Metadata cannot produce an EXIF-free file.** `AddImageFromSource` keeps the exact pixels — stripping tags must not cost a generation of JPEG quality — but Image I/O writes back a structural block of `ColorSpace`, `PixelXDimension` and `PixelYDimension` whatever it is handed. Those describe the image, not the photographer. The TIFF dictionary is kept deliberately too, since it carries orientation and dropping it turns a sideways photo sideways.

**⌘K command bar:** `ShelfCommandSearch` builds its rows from the same `ShelfAction.groups` and the same `isAvailable(for:)` the menus use, so nothing can be reachable in one and missing from the other. Format and size **presets are rows of their own** — typing "webp" should convert, not open a submenu — while the two actions that own a submenu stay in the list to reach their dialog. Ranking is a pure function scored so a typed prefix beats a match buried mid-word, with menu order breaking ties, since `sorted` is not stable and equally good matches would otherwise shuffle between keystrokes. Rows are `Button`s rather than tap gestures: only a real control carries an accessibility action, and without one the list cannot be driven by anything but a mouse. Arrows and Return go through a local monitor, because a `TextField` keeps them for the field editor where they would move the caret and do nothing useful.

**Shelf dialogs:** `ShelfDialog` is one floating panel at a time, hosting the image options and Get Info. A window rather than another `ShelfRoute` — which is what these were at first — because the options are about the files, and swapping the shelf's own contents for a form hides the very items being converted. Its height comes from the laid-out content through `onGeometryChange`, not from `fittingSize`: an unconstrained hosting view answers for whatever width SwiftUI picked rather than the width the window will have, which produced a 340×859 window for 280pt of content. Reading the height back also covers rows that come and go — the pixel field, the quality slider — with no second size to keep in step; the first report positions and shows the window, later ones resize it from the top edge so it does not walk up the screen. The output folder and "show output in" are remembered in `AppState` and used by the presets too, so a preset and the dialog do not disagree about where things go. The chosen folder applies **only when the result is meant to be found** (`ShelfOutputReveal.usesChosenFolder`): sending it to the shelf alone leaves it in OneBar's own folder, and the folder control is hidden rather than sitting there having no effect. A conversion that does not change the format keeps the file's own extension too — `.jpeg` and `.jpg` are both JPEG, and renaming someone's file is not a conversion.

**Inline rename** turns the item's label into an `NSTextField` in place, base name selected and extension not, the way Finder renames a file. It is AppKit because that selection is the point and only the field editor can be told what to select. Three exits, and they must not collide: Return and click-away both commit — and a commit also *ends editing*, hence the `finished` latch, or the name would be applied twice, the second time against an already-renamed item; teardown never commits, since the shelf closing did not mean "keep what was typed"; and Esc is **declined** by the shelf's key monitor rather than handled there, because that monitor sees the key first and closing the shelf out from under an open field would be a surprise — letting it through reaches the field editor's own `cancelOperation:`. The rename itself is a `moveItem` within the same folder, which is what keeps a materialised file a direct child of `shelf-items` and so still owned by the store.

**Instant actions:** a shelf a drag is hovering puts a row of buttons under it, and dropping on one runs that action against the dragged files without them ever becoming items on the shelf. The strip is a **window of its own**, not part of the shelf: the shelf's whole content view is already one drop target, and buttons drawn inside it would have to carve hit regions out of that. It is added as a *child window*, so it follows the shelf with no tracking of its own — which is also why it must not be positioned from a frame the shelf is still sliding through, since a child keeps whatever offset it is given for life; `showInstantActionBar(delayed:)` waits for a peek to settle. Both windows hold each other open across the gap between them (`holdInstantActionBar` / `holdOpen`), because moving the pointer from one onto the other counts as leaving, and without that the shelf would slide back and the strip vanish under a drag aimed at a button. Buttons are `ShelfCommandKind` values, so nothing is reachable here that the menus and ⌘K do not have, and dimming reuses the same `isAvailable` rules against a `ShelfDragPreview` read from the drag pasteboard — deliberately *not* `ShelfItemReader`, which materialises dropped text to disk, and dragging past a button must not write a file. `ShelfInstantActionLayout` is the single source of the tile rectangles for both the SwiftUI content and the flipped AppKit view that catches the drop, so what you see and what accepts a file are the same rectangle by construction. Only a shake leaves a drag in flight over an empty shelf — a notch drop has already consumed the drag — and `isTransient` marks that shelf, because an action whose output goes to Finder may close the container made for one drag but must never close a shelf the user parked at the edge.

**Custom actions:** a registered shell script or `.workflow` appears beside the built-ins in all four action lists. The contract is one sentence each way — **the files arrive as arguments, and whatever is left in `$ONEBAR_OUTPUT_DIR` comes back** — and it runs through the same `produce` as every other writing action, so it gets the progress window and a Stop that reaches the process. Four things are less obvious than they look. `$ONEBAR_OUTPUT_DIR` is a **fresh directory per run**, not `action-output` itself, or there is no way to tell what this run produced from what was already there; results are moved into the real output folder afterwards. A shell script **without its executable bit is handed to `/bin/sh`** rather than refused, since forgetting `chmod +x` is the commonest way this fails. Output goes to a **file, not a pipe** — a script printing more than a pipe buffer holds would block forever waiting for someone to drain it — and that log is read *and deleted* before the outputs are collected so it cannot come back as one of them. And an **empty result is success**, unlike a built-in transform: a script that uploads or files something away has done its job with nothing to show. `ShelfCommandSearch.commands` takes the custom list rather than reading the store, so it stays a pure function and its tests do not depend on what is registered on the machine running them.

**Watched folders:** `FolderWatchService` puts what arrives in a folder onto a shelf, filtered by a rules engine (`ShelfWatchRule`: name / extension / size / kind against an operator, all or any). The screenshot shelf is the same machinery pointed at whatever `com.apple.screencapture`'s `location` says, rather than a second mechanism assuming the Desktop. `FSEventStream` rather than a `DispatchSource` descriptor watch: only FSEvents can see inside subfolders, and a descriptor watch says the directory changed without saying *what*, so every notification would mean re-listing and diffing. One stream covers every watch; the per-watch part is applied when a path is matched back to its watch, which is also how a shallow watch is done since FSEvents is always recursive. Four rules make it liveable. **`SinceNow`** is what stops enabling a watch on Downloads from emptying the folder onto a shelf. **An arrival has to stop growing** before it is taken — a file exists from its first byte, so one caught at creation is often still being written, and a size rule would be tested against a number still climbing; files whose extension says they are still downloading are skipped outright, since the rename that finishes them is the event worth acting on. **A modified file is not an arrival** — only created and renamed count, or saving a document in a watched folder would put it back on a shelf every time. And **one shelf per watch, not per file**, or a burst would ask for a shelf each and hit the open-shelf limit on the third; it never takes focus, because a file arriving is not the user asking for anything.

**Services and `onebar://`:** the two ways in that need no drag, both landing in `ShelfIntegrations` because both answer the same question — some files, and a request to put them somewhere. Three platform behaviours had to be worked around, and each one fails silently. **`NSSendTypes` alone never offers a service on a file selection**: Finder filters that menu by `NSSendFileTypes`, so the entries were registered correctly in `pbs` and appeared nowhere. **macOS registers a new third-party service *disabled***, and a disabled service shows in no menu at all — the feature looks broken with nothing wrong in the app — so OneBar ticks its own entries once on first run by writing `pbs.plist`'s `NSServicesStatus`, whose shape was *measured* from a real click in System Settings and whose keys (`<bundle id> - <menu title> - <NSMessage>`) are built from the app's own `NSServices` array. Written **once ever**, gated on a flag in OneBar's defaults, so a deliberate untick is never overridden. And **SwiftUI routes an incoming URL to a window scene**, which put Preferences on screen for every link until `.handlesExternalEvents(matching: [])` took the only window scene out of that running — it is not an activation problem, and `applicationShouldHandleReopen` does nothing for it. URL parsing is a pure `ShelfURLCommand`, because that is where the edge cases are: `onebar://shelf/close` and `onebar:///shelf/close` put the same word in different halves of the URL depending on slash count, and an empty `?path=` has to mean nothing rather than the root of the disk. Finder also caches the services list past `pbs -flush`, so `killall Finder` is what actually refreshes it.

**Shortcuts:** `ShortcutStore` maps `ShortcutAction` → `KeyBinding` (raw `keyCode` + modifier mask), persisted as JSON. `ShortcutAction.globals` (`openPanel`, `openClickPoints`, `turboClick`, `pickColor`) are the ones registered system-wide; every other binding is matched inside the panel's local monitor. All of them are user-rebindable. `ShortcutsPane` groups them by `ShortcutAction.Section` (Global / Clipboard History / Shelf) rather than the bare `isGlobal` split it started with, which stopped being readable once the shelf pushed the list past twenty entries. Global hotkeys go through `HotkeyManager`, which uses Carbon `RegisterEventHotKey` (permission-free, unlike an `NSEvent` monitor, which would drag in Input Monitoring). It holds several at once, keyed by `GlobalHotkey` — whose raw values are Carbon hotkey ids, so never renumber a shipped case — and the C handler reads the fired id back out of the event with `GetEventParameter` because a C function pointer can't capture anything. Rebinding a global one re-registers immediately — `ShortcutStore` calls `registerFromStore()` itself when the changed action `isGlobal`.

**Permission-gated features:** keyboard cleaning (a `.cghidEventTap` `CGEvent.tapCreate` swallowing key events plus the `NX_SYSDEFINED` hardware-button subtypes — volume/brightness/media/eject/power — behind a `.screenSaver`-level overlay per screen; Touch ID is unaffected because fingerprint reads never produce a CGEvent) and pasting (`PasteService` synthesizes ⌘V via `CGEvent`) both require Accessibility and check `AXIsProcessTrusted()`; both degrade quietly rather than erroring. Scan Text/QR shells out to `/usr/sbin/screencapture -i -c` and needs Screen Recording — the `Process` must be retained in `ScreenCaptureService.runningProcess`, since a still-running deallocated `Process` crashes the app.

**Cursor movement is shared.** `Support/CursorMotion.swift` owns every synthetic pointer move: an eased 60fps path of `.mouseMoved` `CGEvent`s posted at `.cghidEventTap` (a single jump gets coalesced into no visible movement at all), with duration derived from distance ÷ speed so long and short moves look alike, and an optional `curve` that bows the path off the straight line via a quadratic bezier whose control point is randomised in size and side. Every step compares the cursor's actual position against the last one posted and returns `false` if they diverge — our own events land exactly where we put them, so any drift is a real hand on the mouse. Positions everywhere are read via `CGEvent(source: nil)?.location`, already in flipped top-left event space, which is why no multi-monitor coordinate conversion exists anywhere in the codebase except `NSScreen.eventSpaceOrigin` (used only to map nodes into a canvas window's view coordinates).

**Auto Mouse Move:** `MouseMoveService` sweeps the cursor out and back through `CursorMotion` (straight, `curve: 0`), which resets `HIDIdleTime` — the clock Teams/Slack read to decide you're away. In idle-aware mode the timer ticks faster than the configured interval and the nudge is gated on `CGEventSource.secondsSinceLastEventType(.hidSystemState, …)`, so real input postpones it rather than racing it. The return leg only runs if the outward one completed. `mouseMoveNatural` (on by default) curves the path, tilts the sweep off horizontal, varies its length, and jitters the timing — on a fixed schedule that means a one-shot timer re-armed with a fresh interval each tick, since there the interval is the only thing left to be regular; idle mode instead re-rolls its idle threshold per fire. Destinations go through `CursorMotion.clamp` first: a point past the screen edge is clamped by the WindowServer, and the cursor would then not be where we posted it, which `glide` would read as interference. Needs Accessibility, mirrors `SleepPreventionManager` for auto-off and the second status item.

**Auto Click:** three pieces. `ClickSequence` (in `Support/ClickNode.swift`) is the `@Observable` list of `ClickNode`s persisted to `UserDefaults` as JSON; positions are stored in event space so nothing is converted at run time. `ClickCanvasController` puts one transparent borderless `CanvasWindow` per display at `.statusBar` level hosting `ClickCanvasView` — click empty space to drop a point, drag to move, select for the inspector. `AutoClickService` walks the list: travel via `CursorMotion` with the configured curve, scatter the landing point by the jitter radius, act, then wait a delay randomised by the variance fraction. A node acts in one of four ways — click, type, slide or scroll. Typing overrides each event's unicode payload (`keyboardSetUnicodeString` on a `virtualKey: 0` event) instead of mapping keycodes, so it is layout-independent; newlines are sent as a real Return keypress because a literal `\n` in the payload is ignored by most text fields. A slide holds a button down along the path and posts its mouse-up on *every* exit path, since bailing out mid-drag would leave the system holding a button with nothing to release it. A scroll posts `scrollWheelEvent2` events with an explicit `event.location` — wheel events go to whatever is under the pointer, not to whatever has focus — and accumulates emitted distance across steps because integer wheel deltas would otherwise round small per-step amounts away to nothing. A double click is one event stream with `.mouseEventClickState` escalating — two plain clicks read as two singles — and the button is held ~20ms because a zero-length press is dropped by some controls. Three independent stops, because a running clicker owns your input: the Esc kill switch (a Carbon hotkey registered *only while running*, since a permanently held bare Esc would be swallowed system-wide), resistance stop (a `CursorMotion` glide returning `false`), and the auto-off timer. The canvas is flipped to `ignoresMouseEvents` during a run or it eats the very clicks being posted underneath it. `ClickLayoutStore` keeps named setups in `click-layouts.json` beside the clipboard history — on disk rather than in `UserDefaults`, since a layout is a file worth finding and backing up.

**Turbo click:** `TurboClickService` is deliberately *not* part of the sequence — it clicks wherever the pointer already is, reading `CursorMotion.location` every tick so it follows the cursor rather than latching a position. Starting it stops `AutoClickService`, since both drive the one pointer. Rate is capped at `TurboClickService.maxRate` (100/sec); Autoclick's author found macOS locks up past 900. It shares the Esc kill switch by registering the same `.autoClickStop` hotkey while it runs. Both it and the sequence post buttons through `Support/MouseEvents.swift`, so the events are identical — turbo skips the ~20ms hold because at high rates there is no room for one.

**Pick Color:** `ColorPickerService` shows `NSColorSampler`, AppKit's own loupe — sampling happens outside our process, so unlike Scan Text/QR it needs no Screen Recording grant. The sample is converted through `usingColorSpace(.sRGB)` before its components are read, since it arrives in the sampled display's own space and `redComponent` on a non-RGB colour traps. The formatted string (`ColorFormat` in `Support/Models.swift`) just goes on the pasteboard; `ClipboardManager`'s poll picks it up as an ordinary text item, so history and search come free. A `nil` callback is Esc and stays silent, like a cancelled `screencapture -i`.

**Display brightness:** `BrightnessService` picks one of four mechanisms per display, because no single one covers them all. The built-in panel and Apple's own externals (Studio Display speaks no DDC either) go through `DisplayServicesShim` — the private `DisplayServices` framework the brightness keys themselves use, `dlsym`'d and optional throughout, so a symbol Apple drops leaves one display uncontrollable rather than taking the app down. External monitors go over DDC/CI (`Support/DDC.swift`): I²C through the private `IOAVService` inside IOKit, wire format and IORegistry pairing derived from MonitorControl (MIT). Anything that won't talk DDC falls back to the gamma table, and AirPlay/Sidecar screens — which have no backlight and silently ignore gamma writes — are dimmed by `ShadeController`'s black window at `CGShieldingWindowLevel` (above the menubar, `ignoresMouseEvents`). Neither software path goes fully dark: a screen you can't see is a screen you can't undim. A display is "virtual" per CoreDisplay's own info dictionary, falling back to the *shape* of the vendor id — a real monitor's comes off its EDID chip and is 16 bits, while one invented in software gets ASCII ("aapl"/"airp"). DDC channel discovery walks the IORegistry pairing each `AppleCLCD2`/`IOMobileFramebufferShim` (which carries the EDID UUID, serial and registry path) with the `DCPAVServiceProxy` that follows it; matching *scores* candidates — registry path 10, vendor/product 2 each, serial 2 — and claims best-first, with discovery order breaking ties explicitly because `sort` isn't stable and two identical panels would otherwise swap displays between refreshes. Having a channel counts as DDC support; answering a read is a bonus, since plenty of monitors take writes while never replying. All of it runs on `DDCBackend`'s serial queue with a latest-wins coalescer — each I²C exchange sleeps for tens of milliseconds, so a slider drag would otherwise queue a backlog and the monitor would keep drifting after you let go. Tracking is a 0.15s poll rather than a notification, because reading DisplayServices is cheap and getting a private C callback signature wrong crashes the app; a 0.4s `lastLocalChange` window keeps our own writes from dragging the slider back, since the brightness keys *ramp* rather than jump. `forcedSoftware` (keyed on vendor-model-serial, which survives a replug) is the escape hatch for a monitor the probe guessed wrong about. Gamma outlives the process, so `restoreDimming()` runs on quit.

**Prevent Sleep:** `SleepPreventionManager` runs one session at a time, always with something that ends it — `SleepSession` is indefinite, `until(Date)` (the duration presets and "Until…" are the same thing, an end date computed when you pick it), `whileAppRuns`, or `whileFileGrows`. It holds two `IOPMAssertion`s: preventing system sleep says nothing about the display, so without the second the screen still goes dark while the Mac stays up — together they are `caffeinate -di`, system-only is `caffeinate -i`. Closing the lid is a *separate* path that ignores assertions entirely, so `Support/Clamshell.swift` drives it directly through `kPMSetClamshellSleepState` (command 12 on `IOPMrootDomain`'s user client — it reaches C but not Swift, hence the literal). No entitlement, no helper, no password; Amphetamine, sandboxed and App Store signed, does the same. Restoring always writes even with no connection of our own open, because a force quit leaves the switch set with nobody to clear it — which is why `AppDelegate` clears it blind at launch. Do **not** branch on `AppleClamshellCausesSleep`: on Apple silicon it reads `No` at rest while lid close still demonstrably sleeps the Mac. One 1s ticker drives everything (countdown, the file every 5 ticks, the battery every 30) rather than a timer per concern. The download watch is Amphetamine's model — end once the file stops growing — with two wrinkles: finishing *renames* rather than deletes (`Foo.dmg.download` → `Foo.dmg`) so the watch follows the rename in either direction, and a Safari `.download` package is a *folder* whose own size never moves however much arrives inside it, so a directory is measured by its contents. The enclosing folder is read once at pick time, while the user is still at the keyboard: asked an hour later the TCC prompt just sits there unanswered and the session never learns the download finished. Starting a session replaces the current one rather than stacking (two sets of assertions would need two stops), and `tearDown()` is the single release point so no exit path can leave an assertion or the lid switch behind.

**Sound:** `SoundService` drives system volume, mute and output-device switching straight off the CoreAudio HAL, with `Support/CoreAudioProperty.swift` as the leaf helper (address/exists/isSettable/value/setValue/objectIDs/string/channelCount, plus `CoreAudioListener`). Reads are cheap and writes are not, and that asymmetry shapes the whole file. A full read sweep of every device on both scopes is ~1.6ms, so reads stay synchronous on the main actor with no `lastKnown` cache — but a *single* `AudioObjectSetPropertyData` volume write measured 5ms to the built-in speakers, 11ms to AirPods and 17ms to a virtual driver, against a 16ms frame. (An earlier version of this note claimed writes returned "in tens of microseconds" and used that to justify writing inline; that was never measured, and a slider drag stalled the UI outright until it was.) Writes therefore go through a latest-wins coalescer onto `writeQueue` — `BrightnessService`'s machinery with the timing turned around: there the problem is that an I2C exchange *sleeps* for tens of milliseconds, here it is only that the main thread must not be the one waiting. `pending` holds at most the newest value per *(device, scope)*, so releasing a slider leaves no backlog draining into the device. Still no lock and no ramp to wait out. `writeVolume`/`writeMute`/`write`/`scalar` are `nonisolated static` for exactly this reason and take a `memberControls` snapshot rather than reaching for main-actor state. "Has a volume control" is a property of a *(selector, scope, element)* triple, not of a device, so each one is probed down a ladder needing both `exists` and `isSettable`: `kAudioHardwareServiceDeviceProperty_VirtualMainVolume` (`'vmvc'` — the *functions* are deprecated, the selector is not, and it is what Control Center drives) → main-element `VolumeScalar` → per-channel scalars on the device's own `PreferredChannelsForStereo` pair (read = loudest channel, write = scaled by each channel's ratio to the peak, so a channel pulled down stays proportionally down) → `.none`, a disabled slider and a note. A device with no real mute control gets no mute button rather than a faked set-to-0-and-restore, which would be a second, disagreeing mute state that the volume keys and Control Center know nothing about. Enumeration needs output channels **and** `DeviceCanBeDefaultDevice` — the Teams loopback driver has two output channels and cannot be made default, and System Settings hides it for the same reason. Switching sets `DefaultOutputDevice` *and* `DefaultSystemOutputDevice` (app audio and alert sounds are separate properties), the second guarded on `DeviceCanBeDefaultSystemDevice` — but the write alone is not something to believe. Destroying a private aggregate returns before every device-list notification has settled, and a write landing in that window is commonly accepted and then ignored, by Bluetooth drivers especially, so one click was not reliably one output change. `setDefaultOutputVerified` therefore writes, sleeps, reads the default back and compares its *UID*, up to four times with longer settles for Bluetooth. The target is re-resolved from the device list by UID on every attempt, because a HAL `AudioObjectID` is a live handle and not a name — the id that was valid when the menu was drawn can be dead by the time the aggregates are gone. A run that never converges leaves the service fully rebuilt and schedules another refresh, rather than stranding the next click behind `outputSwitchTask`. Two derived lists sit on top of the enumeration: `routingOutputs` drops aggregates, since CoreAudio forbids nesting one inside the private aggregate `AppMixer` builds, and `currentOutputDeviceUIDs` *flattens* an aggregate default to its `ActiveSubDeviceList` member UIDs for the same reason — picking a Multi-Output Device as the system output must not leave per-app taps with nothing they can wrap. `Device` also carries an `icon`, resolved once per UID and cached: the driver's own `kAudioDevicePropertyIcon` image where there is one, else a name-matched SF Symbol (AirPods, HomePod, Studio Display…), else one derived from `TransportType`. Live tracking is `AudioObjectAddPropertyListenerBlock` on a dedicated serial queue — never `nil` (the HAL's own thread) and not `.main` — with the handler stored under a `@convention(block)` type, since Swift imports the listener typealias as an ordinary closure and bridges a *fresh* block per call site, so add-then-remove with "the same closure" would remove nothing and `AudioObjectRemovePropertyListenerBlock` returns `noErr` either way. Echo suppression is *not* brightness's blanket window: DDC ramps and CoreAudio doesn't, and a held volume key steps every ~100ms, so an echo is only ignored while it is near what we just wrote — one that lands far away is a device that took the write and ignored it, and the slider should snap back and show that. `lastWrite` is stamped again when the write actually lands, not only when it was asked for: with writes queued, the echo's clock starts at the far end. Note the volume keys go dead while Keyboard Cleaning is on, since its tap swallows the `NX_SYSDEFINED` subtypes by design; that is expected, and they must not be re-implemented off that tap. The input half is the same ladder at `kAudioObjectPropertyScopeInput` (where the `.none` rung is real — the Continuity iPhone microphone has no volume control at any element), except that there is only `DefaultInputDevice`; the HAL has no system input. The level meter is the expensive part: there is no level property anywhere in CoreAudio (`VolumeDecibels` is the knob's position, not the signal), so `Support/InputMeter.swift` opens the device with an `AudioDeviceCreateIOProcIDWithBlock` IOProc — not `AVAudioEngine`, whose input node follows the system default and so can't meter a non-default device — and that lights the orange microphone dot for as long as it runs. Hence `soundInputMeterEnabled` defaults to off, and even when on the meter starts from `SoundScreen.onAppear` rather than the menu's, which is the real reason `startTracking()`/`stopTracking()` exist. `NSMicrophoneUsageDescription` is mandatory in `Bundle/Info.plist`: without it the process is *killed* on first microphone access, not merely denied.

**System sounds:** alert volume (`com.apple.sound.beep.volume`, float) and "Play user interface sound effects" (`com.apple.sound.uiaudio.enabled`, integer), both keys in `NSGlobalDomain` rather than anything in CoreAudio. `SystemSoundService` reaches them through `CFPreferences` with `kCFPreferencesAnyApplication` — `UserDefaults.standard` would write into OneBar's own domain — at `kCFPreferencesAnyHost`, since neither key is in the current-host domain (`defaults -currentHost read -g` misses them). Writes are inline, unlike `SoundService`'s: a set measured ~1µs and a set plus synchronize ~3µs, because cfprefsd does the real work after the call returns. The effects toggle is confirmed live: with the key at 0, a sound flagged `kAudioServicesPropertyIsUISound` played through `AudioServicesPlaySystemSound` is silent, and audible again at 1, with no relaunch of anything in between. **System Settings is not a live oracle for it** — the Sound pane reads the key when it loads and never again, so its switch keeps showing the old position until you navigate away and back. That staleness is what makes the toggle look broken, and an earlier "confirmed by watching the checkbox flip" was a fresh pane load, not a live read. The screenshot shutter is *not* governed by the key either, so it is useless as a test; the Finder trash sounds in `CoreAudio.component/Contents/SharedSupport/SystemSounds/finder/` are.

The alert-volume key is **stored on a different scale than it is drawn on**: System Settings' slider position is `1 + ln(stored)`, so the stored value runs `1/e ≈ 0.368` at the far left to `1.0` at the far right, and anything below 1/e is off the left end and reads as zero. `SystemSoundService.stored`/`shown` convert, and exactly zero is written as a literal `0` because that is what System Settings writes at the bottom of its own travel. Skipping the conversion does not merely mis-scale the slider, it *silences alerts*: a plausible-looking 0.30 lands at zero. AppleScript's `set volume alert volume` takes the drawn scale as 0...100 (FineTune drives it that way, via an `osascript` subprocess because in-process `NSAppleScript` needs the Apple Events entitlement); writing the key directly needs no automation grant, no subprocess and no debounce. The write **is** live, confirmed by watching System Settings' own slider jump as OneBar's moves — despite never touching coreaudiod's per-device store (`/Library/Preferences/Audio/com.apple.audio.SystemSettings.plist`), which System Settings' own drag updates immediately. Nothing in CoreAudio holds this value: a brute-force scan of 14.8M four-character selectors across the system object and system output device found nothing, the device owns no alert control, and `AudioServicesSetProperty` has no volume property. Do not test any of this by ear — level differences under ~2x are inaudible, output volume confounds them, and ten rounds were lost that way; screenshot the Sound pane and read the slider. The slider previews on release, and plays the sound *itself* — `NSSound` loaded by path with `volume` set from the slider — rather than `AudioServicesPlaySystemSound(kSystemSoundID_UserPreferredAlert)`, which leaves the level to the sound server and so previewed at whatever it last read from the key instead of what was just written: the same loudness at every slider position, which reads as the slider doing nothing. Owning playback means owning what the system used to handle, so the preview checks `soundEffectsEnabled` before making any noise. `com.apple.sound.beep.sound` holds the chosen sound, as a bare name on some systems and a path on others, and it goes stale (seen reading `Bottle.aiff` while the pane showed "Pebble"), so an unresolvable value falls back to a real file — a preview that plays nothing reads as a broken slider.

**Output groups (removed):** OneBar used to publish a named aggregate device — Audio MIDI Setup's "Multi-Output Device" under a friendlier name — that you selected as the system output. It is gone, and per-app routing replaces it — Multi mode does the same mirroring inside each app's own mixer, one app at a time instead of system-wide. The device-level version had to be non-private to be selectable, which meant it genuinely had no volume control at any element, which is why `VolumeKeyMonitor` existed at all: F11/F12 ask the *current output device* to change its own volume, and a multi-output device cannot. That whole layer (`Support/AudioGroup.swift`, `Services/VolumeKeyMonitor.swift`, `VolumeControl.group`/`MuteControl.group`, `reconcileGroups`) is deleted. Doing the same job inside each app's own private mixer needs none of it: the system default stays a real device with real controls, so the volume keys keep working and nothing has to be re-implemented off an event tap. `AppMixer.destroyLegacyGroupDevices()` runs once at launch before the first enumeration — the aggregates live in the HAL, not in our storage, so removing the feature does not take them with it, and a stray would otherwise sit in every app's device list for ever with nothing left to delete it.

**Per-app volume:** `AppAudioService` gives each app its own level without an audio driver, over macOS 14.2+ process taps (`Support/AudioProcess.swift`, `Support/AppMixer.swift`). Background Music and SoundSource both install a virtual sound card and *become* the default output device; OneBar is ad-hoc signed with no installer, so it taps instead. `NSAudioCaptureUsageDescription` is mandatory and the grant is TCC's "System Audio Recording". Seven things here were each established the hard way, and every one of them fails *silently* — the slider simply does nothing:

- **`CATapMuted` alone does not mute.** The header says "no audio is sent from the process to the audio hardware", but a tap nobody reads appears not to run at all. Mute is therefore a gain of zero through the same mixer as every other level — one path, not two, and the working one.
- **The tapped process is not the app.** A browser plays through a helper (`com.apple.WebKit.GPU`), whose parent is launchd, so neither bundle id nor parent pid leads back to Safari. `responsibility_get_pid_responsible_for_pid` (dlsym'd, optional) is how the system itself attributes a helper to its app, and it is what makes "Safari" work. A process with no Dock app behind it is a daemon, not an app — `com.apple.CoreSpeech` holds an audio stream open permanently and must not be offered a slider.
- **One mixer per app, never one shared.** Taps arrive as input streams in an order nothing guarantees matches the order they were listed, so a shared mixer applied Safari's level to Music's audio. A single tap per aggregate makes the mapping trivially right, and keeps adding one app from interrupting another's playback.
- **Never rebuild the mixer unconditionally.** Creating a tap changes the process list and creating an aggregate changes the device list; both fire listeners that land back in `refresh()`, so an unguarded rebuild tears the device down and recreates it forever and never renders a single buffer. Rebuild only when the tap set or output device actually changes.
- **The device-bound tap variant (`processes:deviceUID:stream:`) renders nothing** when its aggregate also holds that same device. It reads like the right API — "streams destined for the selected device" — and it is a dead end; use the plain stereo mixdown.
- **Every output buffer needs writing, and the tap is the *last* input.** A stacked aggregate presents one output buffer per destination, so a render block that fills only `outputs.first` feeds silence to every device after the first. CoreAudio places the single sub-tap after all wrapped hardware input streams, which makes it `inputs.last`; the earlier `min(outputCount, inputCount)` index only happened to agree while there was exactly one output, and picked the wrong buffer the moment there were two.
- **`AudioDeviceStart` returning `noErr` proves nothing.** The HAL reports a start before the aggregate is delivering callbacks, so a route that has not yet produced a buffer is indistinguishable from one that never will. `renderCount` is the only evidence, and nothing may fade away a working route on the strength of a return code alone.

A managed app is routed **whenever it is playing, at every level** (`needsRendering`), because building the route is what costs silence: creating the tap cuts the app's own output instantly while the aggregate, IO proc and first callback take tens of milliseconds to arrive. Paid when a slider crosses 100% that gap lands in the middle of what you are listening to; held open, it is paid once when the app starts making sound, where nobody can hear a late start. This is FineTune's arrangement and the reason its per-app sliders are silent.

Routing only turned-down apps was the earlier design, and holding the route open was tried once and abandoned because *the default output device could not then be changed at all*. **That was ours, not CoreAudio's.** `kAudioAggregateDeviceIsPrivateKey` hides an aggregate from other processes but **not from the process that created it**, so every running mixer came back through `SoundService.refresh()`'s own enumeration as a selectable output called "OneBar App Mixer" — and since creating or destroying one changes the device list, each start or stop fired the device-list listener straight back into a rebuild. `AppMixer.isInternal` drops them before anything reads the list, which is what makes always-on affordable.

With that feedback gone, `syncTaps` leaves a mixer already playing into the right devices alone and hands every other mismatch to `scheduleRouteRebuild`. The old stop-everything-wait-700ms step-out existed to stop mixers "contesting" a switch they were in fact only churning, and has been removed; `prepareForSystemOutputChange` now stops nothing at all, it only cancels and *awaits* any in-flight crossfade, because an explicit route must not leak to System Audio even briefly while a follows-default tap can cross to the accepted device afterwards. `outputDeviceChanged()` compares both the default and the whole `routingOutputs` topology against a snapshot, and *seeds* that snapshot on its first call rather than reading launch as a change. The HAL notifications are coalesced by `SoundService.scheduleRefresh()` (50ms) because a Bluetooth connect fires device-list, default-output and default-input within a few milliseconds and a full refresh re-probes every device.

**Per-app routing:** an app is either `.single` — follow the macOS default (`outputDeviceUID == nil`) or pin one device — or `.multi`, mirroring to every checked destination. The two selections live in separate fields so switching modes never forgets the other, and both `decodeIfPresent` to a default so an older settings file still loads. Multi cannot express "follow the system" and must never hold an empty set: unchecking the last device is refused, because an app with no destination is an app that is not tapped at all, and so quietly back on System Audio while the UI shows nothing selected. A pinned device that is currently disconnected falls back to the system output while keeping the saved preference, so it comes back on replug.

Changing a route is a **crossfade, never a restart in place** (`scheduleRouteRebuild`). The live mixer keeps playing while a second complete tap is built on the new destination; only once that replacement reports `renderCount > 0` is the old one taken to zero and the new one brought up (~120ms), promoted, and only then torn down. Warmup is 50ms, or 300ms when Bluetooth is involved, and a replacement that never renders is destroyed with the original restored at its previous gain — the failure mode is "nothing changed", not silence. Rapid clicks bump `routeChangeGenerations` and the single in-flight task loops until it has caught up to the newest persisted state, so a burst of checkbox toggles never stacks overlapping transitions. `routesChanging` holds the app out of `syncTaps` throughout: creating the replacement aggregate fires the device-list listener, and without that guard the notification reads as the app disappearing and tears down the very route being crossfaded away from.

Only processes actually reporting output I/O are tapped. WebKit leaves several idle CoreAudio helper objects registered, and tapping them made Safari's route churn every time a tab came or went. The process-*list* notification does not fire when an existing helper merely starts or stops audio, so every live process also carries a `kAudioProcessPropertyIsRunningOutput` listener, and both feed a 120ms-coalesced `scheduleProcessRefresh` rather than reconciling against each intermediate state. Because "not playing" is now an ordinary transient, a pinned app's mixer gets a 30s grace period before teardown instead of being dropped the moment it goes quiet.

Two ordering rules in `AppMixer` follow from always-on. The aggregate must be **waited on** (`kAudioDevicePropertyDeviceIsAlive`, pumping the runloop rather than sleeping) before `AudioDeviceStart`: the HAL returns a device before it is usable, and starting a dead one returns `noErr` and then never calls back, which is why the old dropout was a different length every time. And teardown is **off the main actor**, because `AudioDeviceDestroyIOProcID` blocks until the render loop finishes its buffer — inline, it froze the UI thread at the moment the audio needed it. That makes `deinit` subtle: the gain pointers must be freed *by the teardown queue, after* the IO proc is destroyed, never by `deinit` itself, or the audio thread reads freed memory for one last buffer.

Sub-tap drift compensation is a **decision, not a constant**. It resamples the tap against the output's clock, which is right only when they really are different clocks. Over Bluetooth they are not — tap and output both follow the headset — so the HAL adds or drops a sample against the ~50ppm offset about every 0.7s, heard as a rhythmic tick. Off for Bluetooth, on for wired/USB. The render block is real-time — no locks, no allocation, no logging — which is why the gain lives in plain C memory and slides to its target over ~5ms rather than stepping. `AppMixer.renderCount` exists because "started" only means the call returned; a loop stuck at zero renders is the signature failure, and a commented-out row in `SoundScreen` prints it.

**Quitting:** ⌘Q is intercepted, the menu's Quit is not. `QuitConfirmation` puts an `NSAlert` ("Hide" default, "Quit" destructive, plus a suppression checkbox) in front of the shortcut, because for an accessory app ⌘Q is nearly always a misfire from the Preferences window, the clipboard panel or the menu popover. It replaces SwiftUI's `.appTermination` command group rather than implementing `applicationShouldTerminate` — the latter fires for logout and restart too, and a modal alert there is a dialog macOS may cancel the logout over. The panel gets its own `keyCode 12 && .command` branch in `handle(_:)`, since its local monitor sees the event before the (never-drawn, but still live) main menu's key equivalent does; it hops off that callback with a `Task` because a modal loop must not start inside event dispatch. `AppState.quitShortcutBehavior` is a three-state enum, not a Bool: "Don't ask again" means the opposite thing depending on the button it is ticked with, so `.quit` and `.ignore` are separate remembered answers. `.ignore` hides and says nothing — the window going away is the feedback, and a HUD on top of it was noise. Hiding means putting the front window away, which differs per window — Preferences is `orderOut` (not `close`, so the menu can open it again), while the popover is closed by **pressing its status item's button**, since MenuBarExtra keeps no record of the popover beyond that button and hiding the window behind its back leaves it believing the popover is still up, so the next click on the icon is spent correcting that instead of opening it. The item is picked by position — the popover hangs under the item it belongs to, which is what tells it apart from the status items Prevent Sleep and Auto Mouse Move add. Force Quit is unaffected by construction: SIGKILL runs none of this.

**Menubar label:** `MenuBarExtra` mangles stacked/inline views in its label, so the live CPU/MEM readout is pre-rendered to a single template `NSImage` via `ImageRenderer` in `MenuBarLabel.statsImage`.

## Conventions

- Use `.liquidGlass(in:)` (`Support/LiquidGlass.swift`) for glass surfaces rather than calling `glassEffect`/`.ultraThinMaterial` directly — it holds the macOS 26 availability fallback in one place.
- Transient user feedback goes through `HUD.show(_:symbol:)`, not alerts.
- Timers are created with `Timer(...)` + `RunLoop.main.add(timer, forMode: .common)` so they keep firing during menu tracking; callbacks hop back with `Task { @MainActor in ... }`.
- Comments in this codebase explain *why* a non-obvious workaround exists (AppKit quirks, permission behavior). Match that — don't add narration of what the code plainly does.
